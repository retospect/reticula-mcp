# Changelog

## Unreleased

- A share between two people who have no hub between them yet waits until the person it is for accepts it. Until then nothing of the hub reaches them: not its title, not its notes, in no `start`, `search` or `get`. Their `start` names the sharer and the hub's id (at most 5 such lines), with the calls: accept with `share(hub=<id>, person=<yourself>, mode="read" or "add")`, which gives at most what was offered; refuse with `mode="none"`; refuse and stop further shares from that person with `share(hub="<id>:block", person=<yourself>, mode="none")`, which the sharer is not told and which a share of yours to them lifts. While either of two people gives the other read or add on a hub (an accepted share, or a grant from before), shares between them apply at once, as before; after that access is revoked, the next share waits again. Only a direct share counts: a hub of a third person that both read does not. The sharer's `share(hub)` lists the person as waiting. Migration 0304 adds the tables `share_offer` and `share_block`; both are rebuilt from the record log. Grants made before stay as they are.
- A new account is not listed in the directory of people (`search(kind="person")`) until it runs `edit(ref="settings", text="listed: yes")`. Accounts made before stay as they were: migration 0358 writes `listed: yes` for every account that never set it, and changes nothing else. It can still be shared with by its exact handle.
- `search`: among notes whose title is the query, your own come before other people's; then, as before, the newest first. The same holds among notes that carry the query as a tag.
- `delete` asks first. `delete(ref="<id>")` deletes nothing: it names the note, the hubs it is filed in, and the call that deletes it, `delete(ref="<id>:yes-<code>")`, for after the person has said yes. The code is bound to you, the note and its version, and holds for 15 to 30 minutes; after an edit, or later, the first call gives a new one. In the trial, assistants asked a clear request to delete made both calls in one turn in 24 of 48 conversations without the last sentence of the answer, and in none of 48 with it (`docs/trials.md`, "Asking before a delete"). Both calls count against the write limit.

## 0.4.2 (2026-11-26)

- Limits on the tools that only read, per account: at most 300 may start per minute (`RETICULA_READ_RATE`), 4 run at once (`RETICULA_READ_CONCURRENCY`; a further one waits up to 10 seconds, holding no database connection, then is refused), and one may take 20 seconds (`RETICULA_READ_SECONDS`). Over a limit the tool answers in the form of the write limit, for example `read limit reached (300/minute); try again in 12 s`. They are kept in the server's memory, per process.
- `search(query="", since=...)` and `get` of a deleted address tell of a note deleted or taken out of a hub only when it happened while you could read that hub: a share given afterwards does not tell what was taken away before. `get(ref=<note>, depth=2)` counts only notes you may read in its "and N more" line.
- Private keys are encrypted in the database with a secret kept outside it, in the file `RETICULA_KEY_FILE` (AES-256-GCM, each value bound to its account and key). The server and every command refuse to start without the secret, with a key file that others can read, with a secret that does not match the stored keys, or while keys are still unencrypted. Upgrading needs one step with the server stopped: `reticula-mcp key init --file <path>` (or `openssl rand -base64 32`), `RETICULA_KEY_FILE`, then `reticula-mcp key encrypt`, which is safe to run again. `reticula-mcp key rotate --new-file <path>` re-encrypts with a new secret. `RETICULA_KEY_FILE=none` keeps keys unencrypted, for development only. Migration 0355 lets the column hold only the two forms; it changes no row.
- `compose.yaml` mounts the key file `deploy/secrets/reticula.key` into the server as a secret and sets `RETICULA_KEY_FILE`; `compose.dev.yaml` sets `RETICULA_KEY_FILE=none`. The upgrade makes the file, stops the server, runs `reticula-mcp key encrypt` with `docker compose run --rm --no-deps app` and starts it again: docs/operating.md, Upgrade and The key file.
- The server connects to the database as `reticula`, a role that owns the database and has no superuser rights. `compose.yaml` makes the superuser `reticula_admin` (`RETICULA_DB_ADMIN_PASSWORD` in `.env`, never given to the server), and `deploy/db-init/10-owner-role.sh` makes `reticula` and the extensions on an empty data directory. An install from before moves its database into a new volume by a dump and a restore, together with the key file steps: docs/operating.md, Upgrade. A restore as `reticula` needs `pg_restore --no-comments`.
- docs/operating.md: `backup.sh` signs every file it writes with `ssh-keygen -Y sign`, and Check a backup and Restore check the signature first with `ssh-keygen -Y verify`; the guide gives the commands for the signing key and what each failed check prints. `.gitignore` keeps the files of `backup.sh` out of the repository.
- Release workflow: a version tag first runs every check of the repository on the tagged commit, then builds the package once, and only then publishes exactly the files that were built. Only the publishing job can ask PyPI for a token, and it runs no code from the repository. Every action is pinned to a commit.
- Private keys are encrypted in the database with a secret kept outside it, in the file `RETICULA_KEY_FILE` (AES-256-GCM, each value bound to its account and key). The server and every command refuse to start without the secret, with a key file that others can read, with a secret that does not match the stored keys, or while keys are still unencrypted. Upgrading needs one step with the server stopped: `reticula-mcp key init --file <path>` (or `openssl rand -base64 32`), `RETICULA_KEY_FILE`, then `reticula-mcp key encrypt`, which is safe to run again. `reticula-mcp key rotate --new-file <path>` re-encrypts with a new secret. `RETICULA_KEY_FILE=none` keeps keys unencrypted, for development only. Migration 0355 lets the column hold only the two forms; it changes no row.
- Sign-in and accounts: a connector can register only when it returns to this computer or to a known client's host, unless `RETICULA_REGISTRATION=open`, and the same rule applies when it asks a person to sign in; many failed sign-ins for one e-mail address from many networks make further attempts for it wait, up to 30 seconds, without locking the account; sign-up refuses the 10,000 most common passwords (the SecLists list, MIT License); sign-in pages never opened no longer count against a connector's limit of open sign-ins; `reticula-mcp token` makes tokens that expire after 90 days unless `--no-expiry` is given; `reticula-mcp account disable` and `account passwd` revoke every connection and token of the account; a new handle may not contain "reticula" or "admin".
- The image carries the embedding model: it is fetched at build time at a pinned revision, every file is checked against a pinned sha256 (`deploy/fetch-model.py`), and the server runs with `HF_HUB_OFFLINE=1`, so it downloads nothing. `compose.yaml` passes `RETICULA_EMBED_MODEL` to the build; a different model needs `docker compose up -d --build`, and only the models the server knows can be built in. The `reticula-models` volume is no longer used and can be removed with `docker volume rm reticula_reticula-models`.
- `reticula-mcp serve` refuses to start when `RETICULA_PUBLIC_URL` is `https` (or another address that is reached through a proxy) and `RETICULA_TRUSTED_PROXIES` is empty. The error names the URL and says to set the proxy's address; `RETICULA_TRUSTED_PROXIES=none` starts the server as before, with a short warning that every client shares one rate-limit bucket. `migrate`, `token` and `account` are not affected.
- `/healthz` answers from a database check that is at most 2 seconds old, whether it succeeded or failed, so repeated requests do not each take a database connection. The answer itself is unchanged.
- Every check of the repository runs `pip-audit` on the locked dependencies, and Dependabot proposes updates of the Python packages, the GitHub Actions and the base images.
- `compose.yaml`: the database is on a network of its own that only the server joins and that has no route out; the server and the database drop the Linux capabilities they do not need and may not gain privileges, and so does the Tailscale container of `compose.tailscale.yaml`. The server gets the database password as `PGPASSWORD`, so a password with characters such as `@`, `:` or `/` works. No migration.
- The image installs its dependencies from `deploy/requirements.txt`, an export of `uv.lock` with a hash for every file, and the server package without dependencies; `pip check` ends the build if they do not fit. The base images (Python, pgvector, Tailscale, and Caddy in the development stack) are named by digest. The check of the repository fails when `deploy/requirements.txt` is not the export of the lock.

## 0.4.1 (2026-11-26)

- A write that fails now counts against the write limit (`RETICULA_WRITE_RATE`, 600 an hour by default); it did not before. A NUL character or a lone surrogate in any parameter is refused with `BadInput` for every tool before the database is asked; the query of `search` still removes them itself.
- The front page shows "Sign up with an agent" as a button near the top, with one sentence on how signing up works: through the assistant you connect, not a form.
- Hardening of the web pages and the sign-in page: `/hubs` renders any nesting without recursion, shows at most 8 levels below a public hub and at most 2,000 entries, is kept on the server for 10 seconds instead of 60 and sent with `Cache-Control: no-cache`, and answers 503 for a minute when it cannot be rendered; no path is redirected to its form with or without a trailing slash; opening a sign-in page again reuses its form token instead of replacing it, and a page open in another browser says so; at most 4 sign-ins check or set a password at once, and those waiting hold no database connection.
- Request log: a path that holds a space, a quote or a backslash after decoding is written in double quotes, like `agent=`. Other paths are written as before.
- `compose.yaml`: Docker keeps each container's log to 5 files of 10 MB, and the server container may use at most 2 GB of memory (`RETICULA_APP_MEMORY` in `.env` sets another limit) and 512 processes. `compose.tailscale.yaml` and `compose.dev.yaml` get the same log limits. No migration.
- The `cryptography` package is required at 46.0.7 or newer (it was 45 or newer).
- Quoted text: runs of three or more `<` or `>` inside a quoted note show as `‹` or `›`, so only the server writes marker lines, and the begin line says that only an end line with the same 16 hex ends the block.
- Limits on what the tools take, checked before anything is looked up: the `ref` of `get` is at most 2,000 characters and one reference at most 200; a `put` replaces at most 20 notes and takes at most 20 tags. A text with a character the database cannot store (NUL, or a lone surrogate) is refused with a clear error instead of failing inside the server. Titles and tags refuse invisible characters (direction overrides, zero-width spaces, private-use characters); the joiners that emoji and several scripts need are kept. Identifiers no longer match with a line break after them. A deleted address answers as deleted only to someone who could have read the note.

## 0.4.0 (2026-11-26)

- When no note is close enough in meaning to count as a match, `search` adds the up to 3 notes nearest in meaning under the line `closest in meaning, below the match threshold, may be unrelated:`, apart from the results and also beside a keyword match on something else. Your own notes come first with their text; somebody else's are shown without it. A paraphrase whose note scores a little below the cut is found this way: on the test set it brings 2 of the 3 paraphrases the results miss. A query of nonsense gets such rows too, and no result. It adds about 16 ms to a search that shows them, at 30,000 notes, and nothing to one that does not. Only with an embedding model: `RETICULA_EMBEDDER=hash` compares words and shows none.
- Public web pages on the server, plain HTML with no JavaScript, cookies or forms, under a strict Content-Security-Policy: `/` (what Reticula is), `/slides` (the four slides of the deck, the diagrams as inline SVG with their Mermaid source under each), `/hubs` (the public hubs), `/connect` (how to sign up and connect the Claude apps, Claude Code, Codex CLI, Kimi Code or any MCP client, with the connector address taken from `RETICULA_PUBLIC_URL` when the page is served, and the standing line), `/vision`, `/privacy` and `/results` (a benchmark, rendered only from `web/results.json`; until it is measured the page says "Not measured yet." and shows no number). `/hubs` is rendered at most once a minute. The connector at `/mcp` and the sign-in are unchanged.
- `share(hub=<hub>, person="public", mode="read")` puts a hub on `/hubs`, for its owner only, and `mode="none"` takes it off. The page shows the titles and short ids of the hub, of the owner's own sub-hubs in it and of the owner's own notes in them, to anyone, without signing in. It never shows a note's text, a note or sub-hub of another member, a private, deleted or superseded note, a handle, a person ID or an e-mail address. A private hub cannot be made public, `"@public"` stays a handle, and the handle `public` is reserved. The reply says how many notes and sub-hubs it opens and names up to five sub-hubs. Signed-in readers gain nothing from it, and replies that list who reads a hub name it as "the public page", never as a person.
- An owner's own private sub-hub under a public hub shows on `/hubs` as the words "private hub", without its title or id and with nothing under it. Filed with a private filing, it shows nothing at all.
- Migrations: 0.4.0 adds 0354, the SQL function `public_nodes()`, which is all that `/hubs` reads. It changes no table, column or row.

## 0.3.0 (2026-11-26)

- Migrations: 0.3.0 adds 0204, 0205, 0302, 0303, 0350, 0351, 0352 and 0353. They create tables, functions and indexes and change no existing row; 0.2.0 refuses the database afterwards (restore the dump taken before the upgrade to go back). The first start downloads the new default model, bge-base-en-v1.5 (about 210 MB), and the worker embeds every note again in the background; until a note has its new vector it is found by its words only. On a copy of a small live instance that took 20 seconds, and the app used about 620 MB of memory afterwards instead of about 200. Connections made under 0.2.0 keep working (`docs/operating.md`, Upgrade).
- Settings go through one ref on the `edit` tool, with no new tool parameter: `edit(ref="settings", text="word handles: on")`, several one per line or separated by `;`. `profile` lists each setting with its value, its scope and the call that changes it. A bad line is refused with the settings and their values named; `settings` never opens a note, whatever a note is titled (migration 0352, tables `connection_setting` and `account_setting`). In the trials every new tool parameter made assistants skip `start` in some conversations, which a setting through `edit` does not (`docs/trials.md`).
- Word handles: every note and hub has words that name it, taken from the random end of its address, so they never change and are the same on every server. Two to four words, any case, spaces or hyphens between them, work wherever an id does; several notes that share the words give a Conflict that names each with one word more. A note the reader may not read is never named. With `word handles: on` for a connection, each id at the start of a line is followed by its words (`4f9c21aa gentle beacon`), with a third or fourth word where readable notes share the first ones. Off by default. In the trial, assistants talking by voice named notes by their titles and opened the right one in 48 of 48 conversations without the words, so nothing tells an assistant to switch them on.
- `search(query="", since=...)` also lists notes deleted and notes taken out of a hub in that time, as bare lines among the others, newest first and counted in the total: `- 4f9c21aa note deleted by @bea · 3h` and `- 0b7e5d12 note taken out of hub "Board" by @bea · 20h`. A deleted note's line never carries its title or text, and it is shown only to a reader who could have read the note; a note taken out keeps its title only while the reader can still read it. Who may have read a deleted note is answered by one SQL function, `readable_if_live` (migration 0353). In the trial, asked what happened in a hub in the last 24 hours, assistants named all three changes in 46 of 48 conversations against 0 before, and never told the deleted note's content.
- The first `start` of each connection (a connector sign-in or a minted token) points to a new instruction, "How to make Reticula the person's memory in every conversation". It has the assistant answer what the person asked first, then ask once whether to keep their memory in Reticula, and after a yes give the standing line for the app's own memory or CLAUDE.md. Later calls through that connection do not show it again (migration 0351, table `onboarding_shown`). In the trial the pointer came once per connection in 96 of 96 runs, the person's request was handled first in 48 of 48, and after a yes the assistant gave the standing line in 43 of 48 runs against 0. With the line in the client's own instructions, Haiku and Sonnet called `start` first and saved facts mentioned in passing in every run (`docs/trials.md`, round seventeen).
- `get` on a hub of more than 26 notes shows them as lettered groups by subject, at most 26 groups whose sizes differ by at most one, each named by its words. `get(ref="<hub>:A")` reads group A, and `<hub>:AB` a group inside it. The groups go by meaning once every note has its vector and by words until then; the first line says which. The listing asks the assistant to name groups to the person by their words, not by their letters. In the trial, Sonnet's overview of a hub of 223 notes took 12 calls against 73 and 67, Haiku's 26 and 24 against 35 and 50, every overview named all topics (24 of 24 against 19), and Haiku found the three newest notes in 12 of 12 runs against 3. A separate parameter for the letters made assistants skip `start`; the form through `ref` did not (`docs/trials.md`, round seventeen).
- `get` reads up to ten notes in one call: `get(ref="<id> <id> <id>")`, the ids separated by spaces or commas. The line `search` ends with says so; the description of `ref` does not, because a sentence there made assistants skip `start` in the trial.
- The starter names seven relations for `link` (`related-to` as the default, `supports`, `explains`, `qualifies`, `generalises`, `derived-from`, `cites`) and says how to tag: two or three tags a note, lowercase with hyphens, `topic:` and `project:` prefixes. A new instructions note, "How to tag and link notes", says the same at length. The names are those of precis. In the trial, assistants used a relation name outside the set 0 times, against 265 before (`docs/trials.md`, round fifteen).
- The reply of `start` begins with what Reticula is for: the person's own long-term memory, which the next assistant they use reads too, on any model or service. Sharing a hub is named as a separate use. It also asks the assistant to save, without being asked, the decisions, facts about the person's work, preferences and results that a later conversation would need, and to say in one line what it saved. In the trial, facts about a project went into the project's hub more often (12 of 12 conversations against 8), Sonnet saved facts mentioned in passing in 9 of 24 conversations against 0, and nothing private went into a shared hub. The server's instructions keep their first sentence: a new one made assistants skip `start` (`docs/trials.md`, round fourteen).
- The description of `delete` says to delete only the notes that say what the person named, and to keep a note that came up in the same search and says something else. In the trial an assistant deleted such a note with the one asked for in 1 of 72 conversations, against 8 of 72 before (`docs/trials.md`, round thirteen).
- `get` and `search` are faster in a big account. A call now works out once which hubs the account may read. Before, each statement that showed a hub or walked through one worked it out again. At 30,000 notes `get` of a note takes 50 ms instead of 104, `get` of a note that stands three hubs deep in two places 53 ms instead of 224, and `get` of a hub 224 ms instead of 329. A search inside a hub (`hub=`) takes a quarter less time; a search without `hub=` gains little. What a call shows is unchanged.
- `get` of a note names the hub it is filed in by its id at the end of the path: `in: "Lab" / "Lab logistics" id 470547e6`. For a note by somebody else in a hub you may read, it says how to correct it there: `next: put(text=<the correction>, supersedes='2ad253ee', hub='470547e6') replaces it in the same hub`. Before, an assistant asked to correct a note in another person's hub guessed the hub's id in 8 of 24 runs and had calls refused in 9; with these lines it did neither in 24. `docs/trials.md`, round thirteen, has the runs.
- `get(ref=<note>, depth=2)` shows the notes one link step further. Under `two link steps away:` each line names the linked note it goes through, the relation and its direction, and the note reached: `- 2ad253ee link exception-to -> 9f8e7d6c note "Porcelain"`. A note reached twice is shown once, and only notes you may read are shown, at most 30, then `and 5 more: get(ref='2ad253ee')`. Before, `depth` changed only what `get` of a hub showed, and depth 2 on a note printed the same as depth 1.
- `get` of a note with links or replaced versions is faster in a big account: at 30,000 notes 18 ms instead of 225, `get` of a paper 21 ms instead of 189. A hub listing (`search(query="", kind="hub")`) counts the members of each hub in 67 ms instead of 141. What they show is unchanged.
- Every tool that takes a note or a hub (`ref`, `to`, `hub`, `supersedes`) finds it faster in a big account. At 30,000 notes, by address it takes 1.7 ms instead of 38, by short id 1.9 ms instead of 49: a short id is now looked up through the index on the end of the address that the database has had since 0.1.0. What it finds is unchanged.
- A note is findable by meaning as soon as `put` or `edit` returns: when the model is loaded, the note is embedded right after the write commits and before the reply, so nothing is locked while the model runs. With bge-small this adds about 8 ms to a put of a short note and 190 ms to one of 8,000 characters (the model reads the first 4,000). If the model is still loading or fails, the write goes on as before and the background worker embeds the note; a write never fails because of it. A search no longer looks for notes without a vector among all notes on every call, only among those a write could not embed (at 30,000 notes that look took 61 ms per search).
- Migrations: `0302_embedding_backlog` adds two tables: the notes a write could not embed, filled by triggers on the note and vector tables, and the model the worker last finished embedding for. Every note without a vector when it runs goes in once. No existing row is changed.
- The default embedding model is `BAAI/bge-base-en-v1.5` (768-number vectors, 219 MB download), with its instruction in front of every query. On the test set, with 6,000 notes added, it shows 17 of 23 paraphrases at its cut and answers no nonsense query; `BAAI/bge-small-en-v1.5` showed 15 and answered 3 of 6 nonsense queries. It costs about 0.5 GB more memory, about 2 minutes per 1,000 notes to embed instead of 40 seconds, and up to 0.6 s on the answer of a put of a long note. `RETICULA_EMBED_MODEL` chooses another: `BAAI/bge-small-en-v1.5` for a small machine, or `mixedbread-ai/mxbai-embed-large-v1` (1.34 GB, about three times the cost of bge-base, a few more hard paraphrases). Each brings its own cut for matches by meaning. After the switch the server embeds every note under the new model in the background, and a search keeps working meanwhile. The vectors of the old model stay until `reticula-mcp reindex --drop-other-models` removes them, which it does only once the new model has every note; a switch back before that needs no reindex. `docs/operating.md` has the table.
- Migrations: `0303_backlog_current_model` changes one trigger function of 0302: removing the vectors of a model no longer in use puts no note into the backlog. No table, no index and no row is changed.
- `get` of a hub whose text is only its title shows no quoted block around that text: the first line names the title already. That is 118 characters less on such a hub. Every other text is quoted as before.
- Migrations: `0204_readable_hubs` adds the SQL function `readable_hubs` and redefines `readable_nodes` on top of it. No table, no index and no row is changed, and who may read which note is the same before and after.
- Migrations: `0205_current_among` adds the SQL function `current_among`. It answers which of some given notes are current (readable, and not replaced by a newer note) without working it out for every note. At 30,000 notes that takes 2 ms instead of 67 for 20 notes, and 10 ms instead of 120 to 350 for 400. `get` and the search use it where they ask about a list of notes. No table, no index and no row is changed.
- `search` has a `since` parameter: `7d`, `36h`, `2w` or a date such as `2026-11-20`. `search(query="", since="7d")` lists what was written, edited, filed or shared since then, by you and by other people, newest first, and each line says which of these happened. With words in the query it keeps the results that have changed since then. What was in a hub before it was shared with you is not listed as new; the share is.
- `start` says what other people did in the last seven days, after the hub lists and only when there is something: `New from other people in the last 7 days: 3 in "Kestrel", 1 in @bea's hub id 4f9c21aa. List them with search(query="", since="7d").` A hub shared with you in that time gets a line of its own: `Newly shared with you in the last 7 days: hub id 4f9c21aa by @bea.` Your own hub is named by its title. Another person's hub is named by its owner and the id on its line in the hub list, because its title is that person's text and stays in the list that says so. Nothing is stored about what you have seen.
- Migrations: `0350_recent_events` adds three indexes, on the time a note was last changed, on the time a filing was signed and on the log row of each filing. No table, column, function or row is changed. On 30,000 notes they are built in under 50 ms together.
- The replies of `put`, `edit`, `link`, `delete` and `share` name a note or hub by its short id first, the same 8 characters that `search` and `get` print at the start of a line, then its title as one quoted line, then the full address in brackets: `saved note 542b1dbc "Lighthouses migrate in winter" (ret:…/…542b1dbc) in hub 23b6d67b "Coast" (ret:…/…23b6d67b)`. Before, they gave the full address only. A hub you may add to but not read is named without its title.
- A note longer than search by meaning reads gets one more line at the end of the reply of `put` and `edit`: `this note is 6,214 characters; search by meaning reads only about the first 2,200. Split it into notes of one idea each and link them (derived-from or related-to).` The number is what the embedding model reads, title line included. Nothing is refused and the note is stored whole, as before; keyword search still finds words anywhere in it.
- The hub "Reticula instructions" cannot be left: `share` refuses to set your own access to it to `none`, and the next `migrate` gives read access back to every account that had left it that way before.
- When `link` files a note you have also filed in another hub, the reply ends with that hub and the call that completes a move: `still filed in hub 23b6d67b "Garden"; to move it, also run link(ref='542b1dbc', to='23b6d67b', remove=true)`. With more than one other hub it names the first and counts the rest.
- When `link` adds a relation under a name the account has not used before, the reply has one more line with the names in use, most used first, at most eight, and a near one if the new name looks like it: `new relation name "relates-to"; in use: related-to (5), explains (2), supports (1). Did you mean related-to?` A near name is the same after lowercasing and dropping `-`, `_` and a trailing `s`, or at most two letters apart; the recommended names are tried first, then the names in use. The link is made either way. The names the starting instruction recommends (related-to, supports, disputes, explains, qualifies, generalises, derived-from, cites) get no such line on their first use, and `part-of` and `supersedes` are not counted.
- A title is one line. In `put` and `edit`, tabs, line breaks and runs of spaces in a title become one space, and the ends are trimmed. A title with another control character is refused with `[error:BadInput]` and a hint. A note's or hub's title is at most 100 characters, and a longer one is refused with a hint that names the limit; 0.2.0 allowed 200. A paper's title may still have 200. Titles already stored are not changed. `get` shows the whole title in the note's own first line; before, it was cut at 100 characters there too.
- `search(kind="person")` lists the people on this instance: `- @fred (you) · verified: yes · joined 2026-11-25`, by handle, with `search(query="fr", kind="person")` matching part of a handle and an empty query listing everyone. It never shows an e-mail address or a person ID. Every account is listed by default; `edit(ref="settings", text="listed: no")` takes it out (it can still be shared with by its exact handle) and `text="listed: yes"` puts it back. `share` with a handle that does not exist now hints at `search(kind="person")`.

## 0.2.0 (2026-11-25)

- Request log: a refused sign-in says why in a fixed word, for example `reason="signin: bad_credentials"`, `signin: throttled`, `signin: signup_rate` or `signin: link_gone`. A request refused for its `Host` or `Origin` header has `reason="Invalid Host header"` or `reason="Invalid Origin header"` on its line. The other lines of the log, such as a library's warning, now begin with the time in UTC.
- `reticula-mcp connections list` has a `client` column. It holds what the request log prints as `client=` for that connection.
- Search shows notes that have only some of the words. When fewer than three notes are found, notes with some of the words follow under the line `also, with some of the words:`, and each says which it has (`has: kiln, glaze`). A note is added this way only when one of its words is in at most 50 of the notes searched, so a name alone does not bring every note with that name. When no note has all the words, the first line says so: `no note has all of these words; 2 have some of them`. A note found only because it has half of the words or more was a result in 0.1.1; it now stands under that line.
- When more notes have some of the words than are shown, a last line says how many and how to list them: `2 more have some of the words; a search for one of the words alone lists them`. It counts your own notes, the notes of people you gave access to a hub, and the notes in hubs you have filed into.
- Any other note under that line is by somebody else and stands in a hub you have not filed into, or in one that anyone may file into. It is shown without its text, a note without a title as `(no title)`, and at most three of them are shown, after the others. 0.1.1 listed those with half of the words or more as results with their text, however many there were. Notes found in full, by all the words or by meaning, are listed as before.
- The first line of a search says `1 result` for one result.
- The server's instructions end with one more sentence: ids and addresses are for the assistant's tool calls, and it names notes and hubs to the person by their titles. Before, an assistant that saved or listed notes showed the person an id or an address unasked in most conversations. Now it shows an id only when the person asks or when two notes have the same title. The replies of the tools are unchanged. `docs/trials.md`, round ten, has the runs.

## 0.1.1 (2026-11-25)

- Access to a hub covers the hubs filed under it. That is so in 0.1.0 too; its entry below does not say it.

The access list of `share` has `@ben add (through a hub above this one)`, and the `access:` line of `get` has `@ben add (through a hub above)`. A person is named only to someone who may see the access list of that hub above: its owner, or a member who can add to it. Everyone else gets the wording of 0.1.0.
- A member who can add to a hub is told who the people are: `only you and the owner have access`, or `you, the owner and 2 more have access`. 0.1.0 printed `2 people have access` and `4 people have access` for the same hubs.

Both now see `add (from a parent hub)`. The access list says the same of such a reader: `@cleo read (granted by @ben); add through a hub above this one`. Nobody's access changed, only what is printed.
- Search finds a note by a short title inside a long query: `greenhouse gateway SD card replaced` now finds the note titled "Gateway". A title of filler words or numbers only does not match this way.

It no longer compares the query with every title: at 30,000 notes the title part of a search takes 48 ms instead of 130, and 11 ms instead of 1.8 s for a 1,000-character query. A search on a long-lived connection no longer slows down after the fifth search (22 to 127 ms measured). A query of more than 16 words that say something is taken for a pasted text: no title is looked for inside it, and a note is still found by its words.

## 0.1.0 (2026-11-25)

The first release. It is phase one of Reticula: one server that gives AI assistants a long-term memory they can share.

What phase one is:

- An MCP server over streamable HTTP with nine tools: `start`, `profile`, `search`, `get`, `put`, `edit`, `link`, `delete` and `share`. Replies are compact text. Errors read `[error:Code] message` with a `hint:` line.
- Notes (atoms) with a permanent address, `ret:<person id>/<uuid>`. A note is edited by its author as a new version. Anyone else corrects it by writing a note that supersedes it. Old versions and superseded notes stay readable by address.
- Hubs to file notes under, with three presets (`group`, `moderated`, `personal`). A hub is shared with other accounts on the same instance for reading and adding, or for reading only. A note marked private stays with its author even inside a shared hub.
- Search over everything an account may read, by keywords and by meaning. Each result shows an excerpt of the note, so a short note is read without a second call. A search without words is a listing: `search(query="", kind="hub")` lists every hub the account can read, and `search(query="", hub=<hub>)` lists what is filed under one hub. A DOI or arXiv id as the query finds its paper and the notes about it. The extra `reticula-mcp[fastembed]` adds a local embedding model. Without it, keyword matching still works.
- Accounts with an e-mail address and a password, a sign-in page for assistant connectors, and bearer tokens minted on the command line. Connected assistants and tokens can be listed and revoked one by one.
- An Ed25519 signature on every note from the moment it is written. The note format is version zero and is specified in `docs/format.md`.
- Instructions for assistants that ship with the server: a starting instruction returned by `start`, and how-to notes found with `search(kind="instruction")`. Text written by anyone else is quoted as data and is never an instruction.
- Debug notes. An assistant can report a tool that misbehaved, and only the operator reads the report (`reticula-mcp debug-notes`).
- Paper stubs by DOI or arXiv id, and notes anchored to a quoted passage of a paper. A note shows the paper it is about, and a paper lists its notes.
- PostgreSQL 17 with pgvector as the only store, migrations with `reticula-mcp migrate`, and a compose file that runs database and server together.
- Trials with assistants that had never seen Reticula, on Claude Sonnet and Claude Haiku. `docs/trials.md` records what they did and what was changed because of it.

What phase one is not:

- No federation. Two instances do not exchange notes. Addresses and signatures are in place so that it can be added without rewriting notes.
- No encryption. The format has room for it and nothing uses it. Anyone who can read the database can read every note.
- No web interface except the sign-in page.
- No messaging, no review workflow, no paper library and no installer.
- No stable format yet. Version zero of the note format may still change.
- No promise about assistant products other than the ones tried. Check the connector with your own client.
